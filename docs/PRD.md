# FOMO Firewall 产品需求文档

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | FOMO Firewall |
| 产品阶段 | Hackathon MVP |
| 目标赛道 | KeeperHub Agents Onchain 主赛道 |
| 目标网络 | Base Sepolia (`84532`) |
| 目标交付 | 公开仓库、Demo 视频、KeeperHub 真实交易链接 |
| 文档状态 | 已批准方向，待实现 |

## 2. 产品摘要

FOMO Firewall 是一个链上行为防火墙。用户在冷静时先设置追涨纪律。当用户后来因资产快速上涨而产生大额买入意图时，Agent 判断这笔意图是否违反规则。若违反，Agent 不只发出提醒，而是通过 KeeperHub 把准备投入的测试 USDC 锁进链上冷静期保险箱。

冷静期结束后，产品生成两条平行时间线：

- **没有防火墙**：计算如果用户当时立即买入，现在的假设价值。
- **开启防火墙**：展示真实锁仓、退款和最终保留的 USDC。

产品的情绪回报不是“AI 预测对了”，而是让用户看到：提前设定的纪律在一次具体决策中保护了多少钱。

## 3. 问题

### 3.1 用户问题

资产快速上涨时，用户容易把“害怕错过”误认为投资理由，并临时扩大仓位。传统产品通常只提供风险提示，但提示出现时，用户正处于最不愿听建议的状态。

### 3.2 现有方案为什么不够

- 风险弹窗可以被立即关闭。
- 投资建议不能约束真实资金流向。
- 止损只在买入后减少损失，不能阻止追高进入。
- 价格预测无法稳定判断顶部，也会把产品变成交易策略。
- 普通钱包 SDK 可以发送交易，但不会自动提供预演、稳定重试、状态追踪和完整审计证据。

### 3.3 产品机会

用户真正需要的不是另一个“冷静一点”的提醒，而是一条提前同意的执行规则：

> 当我最冲动时，让我过去制定的规则暂时接管资金动作。

## 4. 产品原则

1. **纪律优先于预测**：Agent 判断规则是否被违反，不预测涨跌。
2. **真实约束优先于提醒**：触发保护后必须发生真实链上动作。
3. **确定性规则控制资金**：LLM 可以解释和解析意图，但不能自行改变金额、地址或规则。
4. **反事实必须诚实**：没有发生的买入只能标为“假设结果”，不能伪装成真实交易。
5. **好坏结果都展示**：价格下跌时展示避免的损失；价格上涨时展示错过的收益。
6. **测试网优先**：MVP 禁止主网交易。

## 5. 目标用户

### 5.1 首要用户

经常交易加密资产、知道自己容易追涨，但无法在情绪出现时遵守仓位规则的零售用户。

### 5.2 次要用户

- 希望给 Agent 设置明确资金政策的 Agent 开发者。
- 希望向用户提供交易保护模式的钱包或交易入口。
- 希望把行为规则变成可审计链上动作的社群资金管理者。

### 5.3 非目标用户

- 寻找自动盈利策略的专业交易者。
- 需要毫秒级高频交易的用户。
- 需要主网托管或正式理财建议的用户。

## 6. 核心用户任务

> 当我因为资产暴涨而想临时扩大投入时，我希望系统按我提前设置的纪律暂时隔离资金，并在冷静后告诉我这个决定产生了什么结果。

## 7. 一条清晰的 Agent 机制

```text
如果 1 小时涨幅 >= 用户的最大追涨阈值
且计划投入金额 >= 用户的最低保护金额
那么将 100% 计划资金锁入冷静仓
```

MVP 使用二元判断，不引入复杂风险评分。

### 7.1 默认演示规则

| 参数 | 默认值 | 用户是否可修改 |
|---|---:|---|
| 最大 1 小时涨幅 | 15% | 是 |
| 最低保护金额 | 50 USDC | 是 |
| 冷静期 | 1 秒（Demo） | 否 |
| 保护比例 | 100% | 否 |
| 网络 | Base Sepolia | 否 |

正式产品的冷静期可以是 1 小时或 24 小时，但不进入 MVP。

## 8. 端到端用户体验

### 8.1 设置纪律

用户设置：

- 最大可接受 1 小时涨幅。
- 触发保护的最低投入金额。
- 确认所有 Demo 交易只使用测试网资产。

### 8.2 提交交易意图

用户可以输入：

> “ETH 已经涨很多了，我怕错过，现在想投入 100 USDC。”

Agent 提取：

- 资产：ETH。
- 金额：100 USDC。
- 动作：买入意图。

解析结果必须展示给用户；用户确认后才进入执行。

### 8.3 判断风险

系统读取行情快照并运行确定性规则：

```text
ETH 1h 涨幅：24%
用户上限：15%
计划金额：100 USDC
最低保护金额：50 USDC

结论：触发 FOMO Firewall
```

### 8.4 执行保护

Agent 调用 KeeperHub：

1. 预演精确额度 USDC 授权。
2. 执行授权并确认状态。
3. 预演 `createIntent`。
4. 执行真实锁仓并确认状态。
5. 展示 execution ID、交易哈希和浏览器链接。

### 8.5 展示双时间线

保护生效后，页面同时展示：

| 无保护时间线 | 防火墙时间线 |
|---|---|
| 假设在快照价格买入 | 真实 USDC 已进入 Vault |
| 持续计算假设持仓价值 | 展示真实链上状态 |
| 明确标记“未发生” | 展示 KeeperHub 证据 |

### 8.6 冷静期结算

冷静期结束后，Agent 读取第二个价格快照并计算对比结果。MVP 使用预先承诺的 `refund_after_cooldown` 结算规则，因此 Agent 不会根据行情临时改变规则，而是通过 KeeperHub 执行 `refund`。真实买入或按价格自动释放属于后续版本。

### 8.7 生成 FOMO Receipt

结果卡必须显示：

- 原始意图金额。
- 进入时价格和冷静后价格。
- 无保护时间线的假设价值。
- 受到保护的实际 USDC。
- 避免损失或错过收益。
- 锁仓和退款的交易链接。
- KeeperHub execution ID。
- 使用的用户规则和行情来源。

## 9. 反事实计算

设：

- `A`：计划投入 USDC。
- `P0`：产生意图时的资产价格。
- `P1`：冷静期结束时的资产价格。

假设立即买入的数量：

```text
Q = A / P0
```

冷静期结束时的假设价值：

```text
V_without = Q × P1
```

保护金额：

```text
protected_loss = max(0, A - V_without)
missed_upside = max(0, V_without - A)
```

MVP 不模拟手续费、滑点或 Gas。页面必须注明这一限制，并单独显示真实链上 Gas。

## 10. 功能需求

### FR-01：规则配置

用户可以设置涨幅阈值和最低保护金额。输入必须经过范围校验。

### FR-02：自然语言意图解析

Agent 将自然语言解析为严格结构：资产、金额、动作。解析失败时不得触发交易。

### FR-03：行情快照

系统保存价格、时间、来源和模式。模式只能是 `live` 或 `historical_replay`。

### FR-04：确定性风险判断

资金决策只依赖版本化规则，不依赖自由文本模型输出。

### FR-05：交易预演

每个 KeeperHub 写操作在广播前必须预演。预演失败或 `wouldRevert=true` 时停止。

### FR-06：真实锁仓

Agent 必须通过 KeeperHub 把测试 USDC 存入 Base Sepolia `FomoVault`。

### FR-07：执行恢复

每个业务动作必须在第一次请求前保存稳定重试键。网络结果未知时，只能使用相同键和相同请求体重试。

稳定重试键是指：同一业务动作即使因超时重复请求，也会被识别为同一次执行，避免重复上链。

### FR-08：状态和证据

系统保存并展示 KeeperHub execution ID、状态、交易哈希、交易链接和可用的回执信息。

### FR-09：真实退款

冷静期结束后，Agent 通过 KeeperHub 调用 `refund`，把 Vault 中的测试 USDC 退回 KeeperHub 执行钱包。

### FR-10：双时间线

页面必须清楚区分假设结果和真实链上结果，不允许使用容易混淆的文案或颜色。

### FR-11：诚实结算

价格下跌显示 `Loss avoided`；价格上涨显示 `Upside missed`；价格不变显示 `Capital preserved`。

### FR-12：历史回放标识

Demo 行情使用历史回放时，页面始终显示：

```text
Market data: Historical replay
Onchain execution: Live on Base Sepolia
```

## 11. 非功能需求

### 安全

- 只允许 chain ID `84532`。
- USDC 和 Vault 地址使用服务端白名单。
- 单次锁仓上限默认 100 USDC。
- 授权额度必须等于本次锁仓金额，禁止无限授权。
- LLM 无权生成或覆盖合约地址、金额和 chain ID。
- KeeperHub API key 只存在服务端环境变量中。
- MVP 不接收用户真实私钥。
- Demo 资金预先放入单一 KeeperHub 组织钱包；页面用户是该 Agent 的操作者，不代表独立链上账户。

### 可靠性

- 网络超时后先查询已保存 execution ID，再决定是否重试。
- 每个状态转换只能发生一次。
- 锁仓成功但页面刷新后，可以从本地数据库恢复进度。
- 达到终态后停止轮询。

### 可观测性

用户需要看到：

- Agent 输入和结构化判断。
- 触发的规则版本。
- 每次模拟的成功或失败。
- 广播、确认和退款状态。
- execution ID、交易哈希和浏览器链接。
- 错误原因与下一步动作。

### 性能

- Agent 判断在 3 秒内完成，不含外部行情和链上延迟。
- 页面在每个 KeeperHub 状态变化后 1 秒内刷新 UI。
- 状态轮询遵守 KeeperHub 返回的建议间隔。

## 12. MVP 明确不做

- 主网执行。
- 真实 DEX Swap。
- 价格预测或买卖建议。
- 多币种、多资产或多链。
- 社交媒体情绪抓取。
- 钱包浏览器扩展。
- 自动持续监控用户交易。
- Override Tax。
- 复杂分仓曲线。
- 收益保证或“AI 避免亏损”的承诺。

## 13. 成功指标

### 黑客松有效性

- 至少一笔通过 KeeperHub 执行并在 BaseScan 可验证的真实交易。
- 推荐目标为三笔：approve、lock、refund。
- Demo 从提交意图到展示交易证据不超过 90 秒。
- 评委在 30 秒内能复述产品机制。

### 产品信号

- 用户能正确区分假设时间线和真实时间线。
- 用户能说出触发保护的具体规则。
- 用户能找到交易哈希和退款结果。
- 测试流程不出现重复锁仓或重复退款。

## 14. 验收标准

### AC-01：触发保护

给定 1 小时涨幅 24%、阈值 15%、金额 100 USDC，系统判定 `BLOCK_AND_COOLDOWN`。

### AC-02：不触发保护

给定 1 小时涨幅 8%、阈值 15%，系统不得调用 KeeperHub 写接口。

### AC-03：模拟失败关闭执行

当 approve 或 lock 模拟返回会回滚时，系统不得广播交易。

### AC-04：重复请求不重复锁仓

同一 intent 的重复执行使用相同重试键，并只能产生一个 lock execution ID。

### AC-05：刷新恢复

锁仓后刷新页面，系统仍能展示 intent 状态和原交易链接。

### AC-06：真实退款

冷静期结束后，KeeperHub 执行退款，Vault 状态变为 `REFUNDED`，用户余额变化可验证。

### AC-07：诚实对比

价格上涨时页面不得显示“避免亏损”；必须显示错过收益。

### AC-08：提交证据完整

README、Demo 和提交页面均包含真实交易链接。

## 15. 风险与应对

| 风险 | 影响 | MVP 应对 |
|---|---|---|
| KeeperHub 钱包缺少测试 ETH | 无法广播 | 开发第一小时先充值并完成最小转账冒烟测试 |
| 测试 USDC 不足 | 无法锁仓 | 提前获取并记录余额截图 |
| 合约 ABI 或地址错误 | 模拟失败 | ABI 固定在代码中，地址白名单，广播前预演 |
| Demo 行情不按预期变化 | 无法产生对比 | 使用明确标记的历史回放 |
| LLM 输出不稳定 | 金额或规则错误 | 结构化输出加 schema 校验，决策由纯函数完成 |
| 网络超时导致重复动作 | 双重授权或锁仓 | 请求前持久化稳定重试键，未知状态先查询 |
| 被理解为投资建议 | 合规和信任问题 | 只执行用户预设纪律，明确不预测、不推荐资产 |

## 16. 后续版本

完成有效提交后再考虑：

- 低、中、高风险下的动态分仓。
- 真实限价 Swap 或聚合器集成。
- 用户长期 FOMO Receipt 统计。
- 可选的提前解除成本。
- 钱包或交易入口插件。
- 用户自托管合约账户和更细粒度权限。
